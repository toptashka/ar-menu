# AR-меню: визуализация еды

Веб-сервис интерактивной 3D и AR-визуализации блюд. Позволяет просматривать позиции меню в трехмерном формате (целиком и в разрезе), изучать пищевую ценность (КБЖУ и состав) и проецировать модели на физическую поверхность стола в масштабе $1:1$ с использованием технологии безмаркерной дополненной реальности (SLAM WebAR) в браузере смартфона.

## 1. Назначение и принцип работы

Сервис функционирует как независимый веб-модуль, открываемый по параметризованной ссылке вида:

```text
https://<host>/?dish=<dish_id>
```

Доступ к сервису осуществляется двумя способами:
* **По индивидуальному QR-коду (Офлайн):** В печатном меню рядом с каждой позицией размещается отдельный QR-код, содержащий ссылку с уникальным идентификатором блюда (`dish_id`). При сканировании стандартной камерой смартфона сразу открывается 3D-карточка выбранной позиции.
* **Через внешнее приложение или сайт (Онлайн):** В карточку блюда в мобильном приложении ресторана или службы доставки встраивается кнопка перехода по прямой ссылке во встроенном браузере (`WebView`).

## 2. Пользовательские сценарии

### Сценарий пользователя (Гость)

1. **Инициализация:** Пользователь сканирует QR-код рядом с позицией в меню или переходит по прямой ссылке из каталога.
2. **Режим 3D-предпросмотра (без камеры):**
   * На экране отображается интерактивная 3D-модель блюда на нейтральном фоне. Камера устройства на данном этапе не активируется для экономии заряда батареи.
   * Доступно вращение модели одним пальцем на $360^\circ$ во всех плоскостях и масштабирование жестом щипка (двумя пальцами).
3. **Работа с интерфейсом и составом:**
   * **Режим «В разрезе»:** Боковая кнопка переключает отображение между целой моделью (`model_whole`) и моделью в разрезе (`model_cut`), демонстрирующей внутренние слои блюда.
   * **Шторка КБЖУ и состава:** В нижней части экрана расположена панель с названием позиции и показателями калорийности, белков, жиров и углеводов. Свайп панели вверх раскрывает полный текстовый состав ингредиентов.
4. **Режим дополненной реальности (Поставить на стол):**
   * При нажатии кнопки **«Поставить на стол»** запускается системный AR-режим (`WebXR` / `Scene Viewer` / `Quick Look`) и включается камера смартфона.
   * Устройство определяет горизонтальную плоскость стола и размещает на ней 3D-модель в физическом масштабе $1:1$.
   * Бумажный носитель с QR-кодом не требуется для удержания трекинга. Модель фиксируется в мировых координатах помещения: пользователь может перемещать блюдо по плоскости стола одним пальцем и обходить стол с любой стороны.

### Сценарий администратора (Импорт данных)

1. Администратор переходит в панель управления по маршруту `/admin` и проходит авторизацию.
2. Заполняет форму добавления или редактирования блюда:
   * Текстовые поля: строковый идентификатор (`slug`), название блюда, полный состав.
   * Числовые поля: калории (ккал), белки (г), жиры (г), углеводы (г).
3. Загружает два бинарных файла 3D-моделей: основную модель и модель в разрезе.
4. Сервер проводит валидацию входных данных:
   * Проверка числовых значений КБЖУ на неотрицательность ($> 0$) и соответствие типам данных.
   * Проверка длины текстового описания состава.
   * Проверка расширения загружаемых 3D-моделей (допускается только `.glb`) и максимального размера файла ($\le 5\text{ МБ}$).
5. После успешной валидации файлы сохраняются в хранилище, запись фиксируется в реляционной базе данных, а система генерирует прямую ссылку и QR-код для печати.

## 3. Техническая архитектура

### Стек технологий

* **Frontend:** HTML5, CSS3, Vanilla JavaScript (ES6+), веб-компонент `<model-viewer>` (на базе Three.js и WebXR).
* **AR-подсистемы:**
  * Android: **Google ARCore**.
  * iOS: **Apple ARKit** (с автоматической генерацией `.usdz`-сцены на стороне клиента).
* **Backend:** Python 3.11+, фреймворк **FastAPI**, ORM **SQLAlchemy**, валидация данных **Pydantic**.
* **База данных и хранение:** Реляционная СУБД **PostgreSQL** (или **SQLite** для локальной отладки), файловое хранилище статики для `.glb`-моделей, статический резервный слепок `data/menu.json` для автономной работы на GitHub Pages.
* **Инфраструктура:** Docker, Docker Compose, туннелирование HTTPS-трафика через `ngrok`.

### Принцип пространственного трекинга и масштаба $1:1$

Расчет реальных габаритов объекта выполняется с помощью алгоритмов **SLAM (Simultaneous Localization and Mapping)** и **VIO (Visual-Inertial Odometry)**:

1. В 3D-редакторе модель создается в метрической системе координат ($1\text{ ед.} = 1\text{ метр}$).
2. При активации камеры алгоритм сопоставляет смещение опорных точек текстуры стола на видеопотоке ($30\text{--}60\text{ Гц}$) с показаниями инерциальных датчиков смартфона — гироскопа и акселерометра ($100\text{ Гц}$).
3. На основе полученных данных вычисляется дистанция до поверхности и строится матрица трансформации, проецирующая модель на плоскость в масштабе $1:1$.
4. **Точность позиционирования:**
   * Смартфоны, оснащенные датчиком глубины **LiDAR**: погрешность $< 1\%$.
   * Стандартные устройства с поддержкой **ARCore / ARKit**: погрешность $2\text{--}5\%$.
   * Изменение масштаба модели пользователем в AR-режиме заблокировано параметром `ar-scale="fixed"`.

## 4. Пайплайн подготовки 3D-моделей

Для обеспечения плавной отрисовки ($60\text{ FPS}$) и быстрой загрузки по мобильной сети исходные высокополигональные модели проходят четыре этапа оптимизации в **Blender**:

1. **Оптимизация геометрии (Decimate / Retopology):** Сокращение полигональной сетки с $500\,000+$ до $10\,000\text{--}40\,000$ треугольников (`Tris`).
2. **Запекание текстурных карт (Texture Baking):** Перенос детализации на низкополигональную сетку через карты нормалей (*Normal Map*), шероховатости (*Roughness*) и затенения (*Ambient Occlusion*) в разрешении $1024 \times 1024$ или $2048 \times 2048\text{ px}$.
3. **Создание геометрии разреза (Mesh Slicing):** Формирование второй версии модели путем булева вычитания (`Boolean Modifier`) с текстурированием плоскости среза.
4. **Сжатие и экспорт:** Экспорт в бинарный формат `.glb` (glTF 2.0) с применением алгоритма компрессии геометрии **Draco**. Итоговый размер одного файла не превышает $1.5\text{--}5\text{ МБ}$.

## 6. Схема данных

### Таблица `dishes` (SQL)

| Поле | Тип данных | Ограничения | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `INTEGER` | `PRIMARY KEY, AUTOINCREMENT` | Внутренний идентификатор записи |
| `slug` | `VARCHAR(50)` | `UNIQUE, NOT NULL, INDEX` | Строковый код для URL (например, `burger`) |
| `name` | `VARCHAR(120)` | `NOT NULL` | Отображаемое название блюда |
| `calories` | `INTEGER` | `NOT NULL, CHECK (calories >= 0)` | Энергетическая ценность (ккал) |
| `protein` | `FLOAT` | `NOT NULL, CHECK (protein >= 0)` | Содержание белков (г) |
| `fat` | `FLOAT` | `NOT NULL, CHECK (fat >= 0)` | Содержание жиров (г) |
| `carbs` | `FLOAT` | `NOT NULL, CHECK (carbs >= 0)` | Содержание углеводов (г) |
| `composition` | `TEXT` | `NOT NULL` | Полный текстовый состав блюда |
| `model_whole` | `VARCHAR(255)` | `NOT NULL` | Путь к файлу целой `.glb` модели |
| `model_cut` | `VARCHAR(255)` | `NULLABLE` | Путь к файлу `.glb` модели в разрезе |

### Формат ответа API и резервного файла (`data/menu.json`)

```json
{
  "burger": {
    "name": "Чизбургер классический",
    "calories": 540,
    "protein": 26,
    "fat": 28,
    "carbs": 42,
    "composition": "Булочка бриошь, котлета из говядины, сыр чеддер, маринованные огурцы, красный лук, томатный соус.",
    "model_whole": "./models/burger.glb",
    "model_cut": "./models/burger_cut.glb"
  }
}
```

## 7. Установка и запуск

> **Требование к протоколу безопасности:** Для работы камеры и WebXR на мобильных устройствах требуется соединение по протоколу **`HTTPS`** (либо запуск на `localhost`). При открытии по незащищенному `HTTP` в локальной сети браузер заблокирует AR-режим.

### Вариант 1. Полный запуск с базой данных и API (через Docker / Python + `ngrok`)

1. Клонируйте репозиторий:
   ```bash
   git clone https://github.com/<username>/ar-menu.git
   cd ar-menu
   ```
2. Запустите серверную часть через Docker Compose:
   ```bash
   docker-compose up --build -d
   ```
   *Либо без Docker (локально на Python):*
   ```bash
   pip install -r backend/requirements.txt
   uvicorn backend.main:app --host 0.0.0.0 --port 8000
   ```
3. Создайте защищенный `HTTPS`-туннель к локальному порту `8000` с помощью утилиты **ngrok**:
   ```bash
   ngrok http 8000
   ```
4. Скопируйте сгенерированный `HTTPS`-адрес из консоли `ngrok` (например, `https://a1b2-c3d4.ngrok-free.app`):
   * Карточка блюда: `https://a1b2-c3d4.ngrok-free.app/?dish=burger`
   * Панель администратора: `https://a1b2-c3d4.ngrok-free.app/admin`

### Вариант 2. Автономный запуск (GitHub Pages)

Если бэкенд не запущен, клиентское приложение автоматически переключается на чтение файла `data/menu.json`:

1. Загрузите файлы репозитория на GitHub.
2. В настройках репозитория (**Settings** $\rightarrow$ **Pages**) выберите ветку `main` и корневую директорию `/ (root)`.
3. Откройте опубликованную страницу на смартфоне по адресу:
   ```text
   https://<username>.github.io/ar-menu/?dish=burger
   ```
